# 03 資料模型

本章是系統最穩定的部分。每個實體先有不依賴 Drizzle 的 TypeScript 型別（`domain/entities/*.ts`），Repository 再定義 Drizzle schema（折衷做法見 02）。以下用 Drizzle 語法呈現，重點是欄位、約束與理由。

**通用規則**

- 中介表用 `primaryKey({ columns })` 宣告真正的主鍵（本章部分範例為精簡用 `uniqueIndex()`）。
- `updatedAt` 只有 `defaultNow()` 不會在 UPDATE 時更新；需要的表一律加 `$onUpdate` 🧪 或 DB trigger（iCal 的 ETag 依賴它）。
- IGDB 的數字 enum 一律在 Provider 轉成我方名稱再存（原則二）；未知值存 `other` 或 NULL 並記警告 log，不讓同步失敗。
- `source` 欄位為 `'igdb' | 'manual'` 的表：同步只動 `igdb` 列，不覆蓋、不刪除 `manual` 列。例外：`release_events` 同鍵的 igdb 日期更新時，manual 列標 `removed`（12 §核可、D75）。

## 遊戲 `games`

```typescript
export const games = pgTable("games", {
  id: serial("id").primaryKey(),
  igdbId: integer("igdb_id").notNull().unique(),
  slug: varchar("slug", { length: 255 }).notNull().unique(),
  name: text("name").notNull(),
  summary: text("summary"),
  coverUrl: text("cover_url"),
  firstReleaseDate: date("first_release_date"),            // 排序用冗餘欄位；規則同 release_events.releaseDate
  firstReleasePrecision: datePrecisionEnum("first_release_precision"), // 取最早一筆 release_dates 的 date_format
  gameType: varchar("game_type", { length: 32 }).default("main_game"),  // 對照見 04
  parentGameId: integer("parent_game_id"),                 // DLC／重製連回本體；刻意不設 FK（本體可能尚未同步）
  gameStatus: varchar("game_status", { length: 16 }),      // NULL = 一般狀態；見 04
  popularityScore: integer("popularity_score").notNull().default(0), // 0~1000
  heatLevel: integer("heat_level").notNull().default(0),   // 0~5，0 = 不顯示
  displayNames: jsonb("display_names").$type<Record<string, string>>().default({}), // 同步時預先算好的各語系名稱
  searchText: text("search_text"),                         // 正規化＋CJK bigram，見 06 §搜尋
  similarIgdbIds: jsonb("similar_igdb_ids").$type<number[]>().default([]),
  alternativeNames: jsonb("alternative_names").$type<{ name: string; comment: string | null }[]>().default([]),
  screenshotUrls: jsonb("screenshot_urls").$type<string[]>().default([]), // 前 6 張
  trailerUrl: text("trailer_url"),                         // 第一支影片
  storyline: text("storyline"),                            // 故事簡介（IGDB 只有英文原文）；詳情頁 About 區
  versionParentId: integer("version_parent_id"),           // 這款是哪款遊戲的「版本」（IGDB version_parent，存 IGDB id）；刻意不設 FK（本體可能尚未同步）
  versionTitle: text("version_title"),                     // 版本名稱，例 "Nintendo Switch 2 Edition"
  ageRatingLabel: varchar("age_rating_label", { length: 32 }), // 例 "ESRB M"；對照表 ❓
  releaseGroup: varchar("release_group", { length: 8 }).notNull().default("tbd"),  // /games 依日期分組的組 key（預先計算，0015）
  publisherGroup: smallint("publisher_group").notNull().default(-1),               // /games 依廠商分組的名單索引；-1＝獨立／其他（預先計算，0015）
  lastFullSyncAt: timestamp("last_full_sync_at", { withTimezone: true }),
  createdAt: timestamp("created_at", { withTimezone: true }).defaultNow(),
  updatedAt: timestamp("updated_at", { withTimezone: true }).defaultNow().$onUpdate(() => new Date()),
}, (t) => ({
  nameIdx: index("games_name_idx").on(t.name),
  parentGameIdx: index("games_parent_game_idx").on(t.parentGameId),
  parentTypeIdx: index("games_parent_type_idx").on(t.parentGameId, t.gameType),   // 詳情頁相關內容分組（0014）
  versionParentIdx: index("games_version_parent_idx").on(t.versionParentId),      // 反查某款的其他版本（0014）
  lowerNamePrefixIdx: index("games_lower_name_prefix_idx").on(sql`lower(${t.name}) text_pattern_ops`), // 搜尋候選的「名稱完全相同」（0012）
}));
```

找不到父遊戲時，前端不顯示「本體遊戲」區塊，不是錯誤。

- `parentGameId` 與 `versionParentId` 都存 **IGDB id** 且不設 FK；詳情頁相關內容依 `parent_game_id = 本作 igdbId` 與 `game_type` 分組（06 §遊戲詳情頁、`catalog/domain/related-groups.ts`），版本以 `version_parent_id = 本作 igdbId` 反查，兩者同時指向本作時只算版本。
- `storyline`、`version_parent_id`、`version_title` 與下節的分類關聯**不寫 `change_feed`**（04 的 change_feed 只記上市日變動）。
- `games_lower_name_prefix_idx` 是 `lower(name) text_pattern_ops`，用於搜尋候選補進「名稱完全相同」者（06 §導覽與 header）；`score_provider` 加值與此索引同在 migration 0012。
- **預先計算的分組欄（Z6，migration 0015）**：`release_group` 與 `publisher_group` 只給 `/games?by=date｜publisher` 讀，讀取的 SQL 不重算。
  - `release_group`：日／月精度 `YYYY-MM`、季精度 `YYYY-Qn`、年精度 `YYYY`、沒有日期或精度 tbd 時 `tbd`。唯一規則在 `catalog/domain/game-group-keys.ts`（`releaseGroupKey`）。
  - `publisher_group`：廠商名單（`catalog/domain/publisher-groups.ts`）的索引，依開發商／發行商判定；不在名單內是 `-1`（獨立／其他）。
  - 維護：`upsertGame`／`syncIgdbGame` 寫入首發日期或公司時，在同一個 transaction 重算（04 §分組欄與代表上市列）。全庫補值用 `backfill_game_groups`。
- **瀏覽用 index（Z6，0015、0016）**：名稱排序依語系各一個表達式 index（`games_dname_{locale}_idx`，語系清單是 schema 的 `DISPLAY_NAME_INDEX_LOCALES`，**新增語系要補 index**，沒補時只是變慢）；其餘見 §索引總表。開發 DB（約 32 萬款）實測：0015 在 games 新增約 283 MB index，0016 再加兩個。

## 上市事件 `release_events`

一列 = 一款遊戲 × 一個平台 × 一個地區 × 一個上市階段（D5、D49）。這是最重要的結構決策：不同平台、地區常不同天，iCal 也需要每個組合各自穩定的 UID。

```typescript
export const datePrecisionEnum = pgEnum("date_precision", ["day", "month", "quarter", "year", "tbd"]);
export const releaseStatusEnum = pgEnum("release_status", ["scheduled", "delayed", "released", "cancelled"]);
export const sourceStatusEnum = pgEnum("source_status", ["active", "removed"]);  // 「來源還有沒有這筆」，不等於取消（D7）
export const releaseStageEnum = pgEnum("release_stage", ["unspecified", "full", "early_access", "beta", "alpha", "demo", "other"]);

export const releaseEvents = pgTable("release_events", {
  id: serial("id").primaryKey(),
  gameId: integer("game_id").notNull().references(() => games.id, { onDelete: "cascade" }),
  platformId: integer("platform_id").notNull().references(() => platforms.id),
  regionId: integer("region_id").notNull().references(() => regions.id),
  releaseDate: date("release_date"),   // 代表日期（P24）：day = 當日；month = 當月第一天；quarter/year = 期間最後一天；tbd = NULL
  periodStart: date("period_start"),   // 期間第一天；day/month 同 releaseDate；tbd = NULL
  precision: datePrecisionEnum("precision").notNull().default("day"),
  status: releaseStatusEnum("status").notNull().default("scheduled"),
  releaseStage: releaseStageEnum("release_stage").notNull().default("unspecified"), // 未知一律 unspecified，不預設 full
  sourceStatus: sourceStatusEnum("source_status").notNull().default("active"),
  sequence: integer("sequence").notNull().default(0),   // iCal SEQUENCE，見 08
  source: varchar("source", { length: 32 }).default("igdb"),
  sourceUpdatedAt: timestamp("source_updated_at", { withTimezone: true }),
  createdAt: timestamp("created_at", { withTimezone: true }).defaultNow(),
  updatedAt: timestamp("updated_at", { withTimezone: true }).defaultNow().$onUpdate(() => new Date()),
});

export const releaseDateHistory = pgTable("release_date_history", {   // 延期篩選與改期紀錄
  id: serial("id").primaryKey(),
  releaseEventId: integer("release_event_id").notNull().references(() => releaseEvents.id, { onDelete: "cascade" }),
  oldDate: date("old_date"), oldPrecision: datePrecisionEnum("old_precision"),
  newDate: date("new_date"), newPrecision: datePrecisionEnum("new_precision"),
  changedAt: timestamp("changed_at", { withTimezone: true }).defaultNow(),
});
```

資料庫只存結構化的日期與精度，**不存已本地化的標籤**（D37）；顯示時由 `formatReleaseLabel()` 依語系組字（06）。

**狀態機**

| 轉換 | 觸發 |
| --- | --- |
| → `delayed` | 新日期晚於舊日期，或精度變粗（day → quarter） |
| `delayed` → `scheduled` | 日期提前或精確化 |
| `scheduled`／`delayed` → `released` | 精度為 day 且日期已過（04 §自動轉 released） |
| → `cancelled` | IGDB 上市日狀態為 Cancelled、遊戲層級為 cancelled，或人工；兩者都不成立時回到 `scheduled` |

「延期」篩選看 `release_date_history`，不看 `status`。日期或 status（取消／復原）變動時 `sequence + 1`。

### 代表上市列 `release_picks`（Z6，migration 0015）

一列 = 一款遊戲 × 一個平台 × 一個上市階段，指向聚合規則挑出的那一筆 `release_events`（地區偏好 WW）。只用來讓平台頁「全部遊戲」先決定這一頁有哪些遊戲，再只對那一頁跑真正的聚合（06 §平台頁的「全部遊戲」）。

```typescript
export const releasePicks = pgTable("release_picks", {
  gameId: integer("game_id").notNull().references(() => games.id, { onDelete: "cascade" }),
  platformId: integer("platform_id").notNull().references(() => platforms.id),
  releaseStage: releaseStageEnum("release_stage").notNull(),
  releaseEventId: integer("release_event_id").notNull(),
  releaseDate: date("release_date"),
  precision: datePrecisionEnum("precision").notNull(),
}, (t) => ({
  pk: primaryKey({ columns: [t.gameId, t.platformId, t.releaseStage] }),
  platformDateIdx: index("release_picks_platform_date_idx").on(t.platformId, t.releaseDate.desc().nullsLast(), t.gameId),
  platformGameIdx: index("release_picks_platform_game_idx").on(t.platformId, t.gameId),
}));
```

- 挑選規則與聚合共用同一段 SQL（`repository/release-aggregate.ts` 的 `buildReleasePicksQuery`，同一組 keys／picked CTE），不另寫一份。
- 維護：所有改動 `release_events` 的正式寫入路徑（`applyReleaseDiffPlan`、`upsertReleaseEvent`）在同一個 transaction 內呼叫 `refreshReleasePicks`，刪掉該遊戲的舊列、整批重算。**繞過這兩個路徑直接寫 `release_events` 的程式（例如測試直接 insert）要自己補**，否則平台頁「全部遊戲」會漏列；`backfill_game_groups --restart` 可修復。
- 開發 DB 實測約 41.6 萬列、69 MB。

## 評分 `ratings`

三個維度分開記（D8）：`scoreOrigin`（哪個評分系統）、`scoreProvider`（從哪個 API 拿到）、`scoreType`（哪種量表）。**玩家評分的原始資料不存這張表**（D68，見 09 §遊玩紀錄）；唯一例外是第二輪的 `site_players` 來源：accounts 排程 `publish_player_ratings` 每小時把「人數達 `PLAYER_RATING_MIN_COUNT`」的站內玩家平均**整批複製**進來（`scoreOrigin=site-players` 類、`scoreType=user_average`、`score` 為平均×10 的 0～100 整數、`reviewCount` 為人數，不分平台），純粹給評分排名頁排序用（06 §評分排名）；它不進詳情頁的來源選擇（05），人數降到門檻以下的舊值會被整批取代時刪除。唯一權威仍是 `game_player_ratings`。

```typescript
export const scoreProviderEnum = pgEnum("score_provider", ["igdb", "opencritic", "metacritic_scrape", "site_players"]);

export const ratings = pgTable("ratings", {
  id: serial("id").primaryKey(),
  gameId: integer("game_id").notNull().references(() => games.id, { onDelete: "cascade" }),
  platformId: integer("platform_id").references(() => platforms.id), // NULL = 來源本來就不分平台
  scoreOrigin: varchar("score_origin", { length: 32 }).notNull(),   // 'metacritic' | 'igdb-aggregate'
  scoreProvider: scoreProviderEnum("score_provider").notNull(),
  scoreType: varchar("score_type", { length: 32 }).notNull().default("critic_aggregate"), // | 'metascore' | 'user_score'
  score: integer("score"),               // NULL = 查過但沒有分數（負向快取），顯示層忽略
  scoreMax: integer("score_max").default(100),
  reviewCount: integer("review_count"),
  sourceUrl: text("source_url"),
  fetchedAt: timestamp("fetched_at", { withTimezone: true }).defaultNow(),
  nextRefreshAt: timestamp("next_refresh_at", { withTimezone: true }), // IGDB 列為 NULL，不進排程
}, (t) => ({
  uniq: unique().on(t.gameId, t.platformId, t.scoreProvider, t.scoreType).nullsNotDistinct(),
  refreshIdx: index().on(t.nextRefreshAt),
}));

export const scoreSnapshots = pgTable("score_snapshots", {   // 分數或評論數變動才寫
  id: serial("id").primaryKey(),
  ratingId: integer("rating_id").notNull().references(() => ratings.id, { onDelete: "cascade" }),
  score: integer("score"), reviewCount: integer("review_count"),
  recordedAt: timestamp("recorded_at", { withTimezone: true }).defaultNow(),
});
```

- **NULL 與 UNIQUE**：Postgres 預設不把兩個 NULL 視為相同，`platformId = NULL` 時一般的複合 unique 擋不住重複（D-Bug3）。用 `UNIQUE NULLS NOT DISTINCT`（PG15+，Drizzle `unique().nullsNotDistinct()` 🧪），即可正常用 `ON CONFLICT`。
- 新來源若有依平台拆分的分數，要填對應的 `platformId`，不能圖方便丟 NULL。
- `score_snapshots` 保留策略：超過 1 年只留每月一筆。

```typescript
// UNIQUE (user_id) WHERE feed_type = 'following' AND revoked_at IS NULL
```

Feed URL 是 bearer token：256-bit 亂數，URL 不含 user_id 或 email。安全規則見 08。

**`change_feed` 規則**

- 與變更**同一個 transaction** 寫入：diff 同步、狀態轉換、自動轉 released（一次 `INSERT … SELECT`）、核可的人工更正。
- 消費者是「至少一次」語意，必須冪等；處理完才更新 `lastChangeId`。消費者：`notifications`、`discord`（伺服器追蹤、身分組 tag）。
- 保留 180 天；消費者落後到 cursor 被清掉時，做一次完整重新同步。
- 既有的 iCal（客戶端拉取＋ETag）與 Discord 活動 reconcile（狀態比對）不改成吃 `change_feed`。

```typescript
interface PopularitySignal {
  readonly name: string;   // 'site_follows' | 'site_follows_7d' | …
  fetch(q: { gameIds?: number[] }): Promise<Array<{ gameId: number; value: number }>>;
}
export const gamePopularitySignals = pgTable("game_popularity_signals", {
  gameId: integer("game_id").notNull().references(() => games.id, { onDelete: "cascade" }),
  signalName: varchar("signal_name", { length: 32 }).notNull(),
  value: integer("value").notNull(),
  updatedAt: timestamp("updated_at", { withTimezone: true }).defaultNow(),
}, (t) => ({ pk: primaryKey({ columns: [t.gameId, t.signalName] }) }));
```

| 訊號 | 來源 |
| --- | --- |
| `site_follows` | `accounts`：`follows` 中 `targetType='game'` 依遊戲計數（停權帳號不計） |
| `site_follows_7d` | 同上，近 7 天新增 |
| `igdb_hype` | IGDB `popularity_primitives` 類型 10（Most Wishlisted Upcoming）與 2（Want to Play）、`hypes`；`value` 只用來排序 |
| `structural` | `aggregated_rating_count`＋平台數＋地區數 |

**計算**（`refresh-popularity`，未上市與上市 30 天內每小時，其餘每日）：

1. 收集各訊號寫入 `game_popularity_signals`。
2. 分兩群：`upcoming`（未上市或上市 ≤ 30 天）、`released`。各訊號在群內取 `PERCENT_RANK()`。
3. `popularityScore = round(1000 × (wSite·pSite + wIgdb·pIgdb + wStruct·pStruct))`；`wSite = 0.6 × min(1, 全站追蹤總數 ÷ HEAT_COLD_START_FOLLOWS)`，其餘權重按 IGDB 0.7／結構 0.3 分配（無 IGDB 訊號全給結構）。缺訊號視為 0。
4. `heatLevel`：群內前 1% → 5、5% → 4、15% → 3、40% → 2、其餘 → 1；**完全無訊號 → 0**。

權重與門檻是起始值，未經驗證（P14）。**防灌水**：追蹤需登入、每人每日新增上限 `FOLLOW_MAX_PER_DAY`、停權帳號不計。**隱私**：追蹤清單不公開；人數低於 `FOLLOW_COUNT_MIN_DISPLAY` 不顯示數字（D48）。
