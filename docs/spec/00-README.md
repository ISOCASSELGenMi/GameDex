## 五個硬性原則

任何章節看起來與這五條衝突時，以這裡為準。

1. **分層依賴方向不可逆**：易變的（UI、框架、第三方格式）只能依賴不易變的（領域模型、業務規則）。見 02。
2. **外部格式不進領域層**：IGDB 的 unix timestamp、Metacritic 的欄位名、Discord 的 snowflake 字串，只能存在 Provider 層，進 Repository／Domain 前一律轉成我方型別。第三方改版，影響範圍只到那一個 Provider 檔案。
3. **有法律或授權風險的整合，做成可獨立關閉、預設關閉的模組**：目前只有 Metacritic 抓取（05）。**兩道開關都開才會抓**：環境變數 `METACRITIC_SCRAPE_ENABLED`（預設 false；false 時模組根本不載入）＋後台設定「允許抓取」（`metacritic.scrapeAllowed`，預設關；12 §設定頁）。任何一道關閉，系統其餘部分完全正常，且不發出任何請求。
4. **功能以模組為單位，邊界由 CI 強制**：追加或移除一個功能，不牽動其他功能。必選的 `catalog` 永遠不 import 可選模組，也不寫 `if (discordEnabled)` 這類判斷。見 02。
5. **同一份邏輯只實作一次**：評分顯示、聚合規則、篩選、日期格式化，頁面、API、Bot、iCal 都呼叫同一個函式（D-Bug7 的教訓）。

## 維護規則

- **一個主題只在一個檔案寫一次**，其他檔案用連結引用（例如「見 03 §releases」）。
- **正文只寫現行規則**，不寫「原本是…後來改成…」。改了什麼寫進 CHANGELOG；為什麼這樣選寫進 90。
- **實測數據與推論過程寫進 91**，正文只留結論與一個連結。
- 產品擁有者的決定寫進 01 的產品決策表，附日期。
- 需求編號沿用功能需求規劃書（`FR-模組-序號`），方便追溯。
