### 我做的判斷（規格沒寫死，請確認）
- **games.parentGameId 存本體的 IGDB id**（不是我方 id）：03 說「刻意不設 FK，本體可能尚未同步」，只有存 IGDB id 才能表達。
- **遊戲層級 cancelled 也把 tbd 列標 cancelled**：規格寫 `releaseDate >= 今天`，SQL 下 NULL 不成立；但未定日的取消遊戲若仍顯示「預定」不合理。
- **建立時就判斷 released**（day 精度且已過），不先建 scheduled 再由自動轉換改：避免回填時每筆多一則 status_changed。
- **game_platforms 不含手機平台**（與 release_events 一致，P35）。
- **「今天」用 UTC 日期**（IGDB 日期是 UTC）；台灣午夜上市的遊戲最多晚 8 小時轉 released。
- **第一次執行（沒有 sync_state）往回看 24 小時**；正式資料靠回填。
- 未收錄的連結來源照規格歸 `other`，每款去重後只留一筆 other；同一個 id 的警告每輪只記一次。

- IGDB 分數消失時寫 `score=NULL`（保留 snapshot 歷史），不刪列。
- 不取 `age_ratings`（對照表 ❓，Phase 3b）、`hypes`（熱度另案）。

`npm run job -- backfill_games [--max-batches N] [--restart]`。進度在 sync_state `igdb_backfill` 的 cursor（JSON：phase recent→undated→done、afterId、firstReleaseFrom 第一次開始時固定）。

IGDB 單頁回應 1.8～14 秒不等，改為「寫入這批時預先抓下一頁」後，剩下約 9 萬款 7.3 分鐘跑完（原本約每批 35 秒）。
完成後：games 105,703、release_events 173,871、igdb slot 重複 0、removed 0；增量同步照常。

### 判斷（請確認）
- **(a) 也限白名單類型**：規格 (a) 沒寫類型條件，但 Tier 3 定義為「DLC、合集、mod 等其餘類型，後置」，所以兩個條件都加白名單（不加的話 (a) 多約 1.2 萬款 DLC 等）。增量同步仍收全部類型。
- **每款一個 transaction、每批寫完才推進 cursor**（規格寫「每批一個 transaction」）：中斷時重做該批，寫入是冪等的，效果相同；單款失敗不拖垮整批。失敗 id 記在 `sync_state.meta.totals.failedIgdbIds`，cursor 照樣推進，任務標失敗。
- 每款寫入先取 advisory xact lock（回填與增量同步可能同時寫同一款；release_events 刻意沒 unique）。
- 白名單常數 `WHITELIST_GAME_TYPES` 固定在 Domain，不跟顯示用的 `CALENDAR_VISIBLE_GAME_TYPES` 環境變數連動。
- 規格要求正式環境「以一次性 container 執行、先備份」；本機是直接 npm run job，部署（Phase 9）時再補。
- Windows 上用工具停止背景 shell 不會停掉子 node 行程（session lock 會被佔住），要另外結束 node 行程。
